# 标准 PRD

## 标准章节

PRD 始终以九章组织。边界必须写清，但不能用边界和功能清单代替完整文档。

| 章节 | 说明什么 |
| --- | --- |
| 1. 版本说明和范围 | 基本信息、背景依据、用户价值与业务目标、成功指标、重要方案决策、本次做/不做、本版功能清单、已有能力影响 |
| 2. 用户与业务流程 | 角色、典型场景与关键任务、前置条件、适用时的模块流程图（含正常、异常路径）、跨模块交接及必要业务对象说明 |
| 3. 功能需求与规则 | 业务模块 → 功能；按适用性展开入口、字段/内容、操作结果、规则及流程图、异常恢复、边界用例与验收 |
| 4. 数据与埋点 | 指标定义、事件触发、字段口径、去重、隐私与验证方式 |
| 5. 非功能需求 | 实际涉及的性能、安全、兼容、可用性、可访问性及合规要求 |
| 6. 验收与上线条件 | 验收范围及规则引用、发布前提、监控、回退、效果验证和执行责任 |
| 7. 里程碑与计划 | 阶段交付物、负责人、依赖、日期与完成条件 |
| 8. 风险与待决策 | 具体问题、影响、建议决策角色和处理状态 |
| 9. 附录与参考资料 | 术语、参考依据、正式设计稿、接口契约及附件 |

信息来自已确定产品方案，不重新做用户痛点研究。计划、指标和技术约定没有依据时写待确认；不适用用简短理由说明。章节可简短，不能以空占位交付。

## 背景、目标与决策

这些内容融入原有章节，不新增菜单。采用短段落或小表格；简单功能可以合并表达，不要求每项独立小节。

- **基本信息（第一章）**：需求/版本名称、产品负责人、文档评审状态、关联项目。项目名称、版本号等已有元数据直接引用；文档评审、业务规则确认和研发进度分别描述，不以“资料已提供”代替评审通过。未知姓名、评审结论和项目关联不猜测。
- **背景依据（第一章）**：方案来源、当前做法/现状、需要改变的问题、已有证据及出处。确定方案仍需说明背景；只整理已有材料，不重新挖掘痛点，不把目标写成已经证实的问题。不具备现状、数据或访谈时明确缺口，不编造调研证据。
- **目标与成功指标（第一章）**：分别说明用户获得什么、业务希望改变什么。适用时列指标名称、基线、目标及依据；未知值标待确认。指标计算、统计对象、分母、时间范围、排除项及数据来源只在第四章维护，第一章引用。仅展示/文案修改不强设转化或营收指标，可说明适用的定性评价方式。
- **关键场景（第二章）**：用“什么角色，在什么情况下，要完成什么任务”说明主要场景。权限表不能代替场景；功能详情只补充局部前提，避免全篇复制。
- **重要决策（第一章）**：对影响范围、体验、依赖或风险的重大取舍，简述已选方案、选择理由、关键假设及依据；有真实备选再记录备选及未采用原因。确定方案没有比较记录时写“未提供”，不补造被否决方案，也不重新打开已确定决策。假设不是事实；尚未解决且影响方案的事项引用第八章。
- **效果验证（第六章）**：引用目标指标，说明观察人群/版本、时间窗口、比较依据、复盘责任角色、如何根据结果决定继续/调整。缺少基线或对照时说明只能描述观察值，不能证明收益由本次改动导致。未明确发布策略时不自动增加 A/B、灰度平台或新埋点功能。

**功能验收与效果验证分开**：验收检查功能是否按规则实现，完整 GWT 在第三章；成功指标检查上线后是否达到目标，第四章定义口径，第六章安排观察。原型检查、验收通过和业务收益不能互相替代。未上线时交付验证计划，实际结果写入验收/复盘台账，不预填“目标已达成”。

缺口按影响处理：会改变范围、权限、核心结果或阻塞实施的事项明确提出；不影响本轮出稿的信息标待确认并继续，不为收集完整背景而反复追问。

## 本版功能清单

第一章先展示“背景与目标”，紧接“本版功能清单”，再展开范围边界、依赖、决策及基本信息等内容。网页与完整 PRD 导出保持同一顺序。

第一章必须有本次功能或版本的功能 list，使读者先知道本版有哪些功能，再下钻详情。默认包含模块、功能名、范围摘要、变更类型、优先级与确认状态；编号用于关联，不能用编号替代名称。

新增/修改/移除/沿用依据当前 spec 与基线对比。同一版本仅将待确认改为已确认，不标为功能修改。首版登记全部新增功能；继承功能标沿用，不能把整套产品功能当成本次新增范围。功能清单是范围索引，不复制业务规则正文；第三章链接回此清单。

CTO 主要通过标准大纲、目标范围、功能清单、依赖风险和计划评审整体方案，不以原型布局作为主要决策依据。开发与测试继续阅读规则和验收详情。

## 内容层次与表达

功能内部的详细结构及易漏项见 [functional-detail.md](functional-detail.md)。不依靠原型补全字段和操作规则；简单功能可以合并表达。

- 标题用于定位：章 → 业务模块 → 功能 → 规则分类。短功能少分层，不把每句话都做标题。
- 功能先说明用途、适用对象和前置条件，再说明正常行为、条件分支、结果、必要异常与恢复。
- 一条规则一个约束；写清字段含义、条件、动作、结果与数值单位，避免读者猜测。复杂分支用表格；抽象规则配一两个必要实例。
- 不为少字省略关键限制，也不反复解释相同背景。PRD 的“简洁”以开发无需猜测、测试能写用例、设计能识别状态为准。
- 通用规则只写一次，页面状态只说明差异；正文不重复原型布局描述。编号和来源在次要层级，确认状态不能隐藏。

## 数据与导出

`content/prd.json` 登记九章及其源文件。范围来源 overview/index.md，功能与验收来源 spec.json；原型引用同一份规则。requirements[].module 表示业务模块，rule_details.category 表示规则分类。

章节状态用 `<!-- prd-status: provided/pending/not_applicable -->` 和 `<!-- prd-reason: 原因 -->` 声明。provided 表示资料已给出，不等于规则已确认。完整 Markdown 导出包含九章，保持章、模块、功能、分类的真实层级，不重复嵌入整份 PRD；验收章引用功能内的验收 ID，不再复制验收正文。

## 附件实际保存

通过 `scripts/edit_project.py <项目根> --version <版本>` 启动本机编辑器，在物料选择中打开“附录 · 文件附件”。选择文件、填写说明、可选关联需求编号、确认分享范围后上传。未保存的正文草稿必须先保存或明确丢弃，避免上传刷新覆盖草稿。

文件保存为项目根 `attachments/<唯一ID>/file.<扩展名>`；同名文件不会覆盖，meta.json 保存原名、说明、版本、时间、关联需求、大小和 SHA256。规划版在 content/attachment-refs.json 绑定 ID 和摘要；后续冻结/交接继承引用。复制、压缩、备份或部署项目时必须包含 attachments 目录，单独发送 HTML 不能携带附件。

冻结后上传进入项目级补充资料，明确标注“冻结后补充”，不写冻结版本，也不冒充原交接依据。补充资料不会自动进入下一版范围；如需纳入，由 Agent 明确登记引用并验证。上传为追加操作，暂不提供删除/替换 UI；修改资料使用新附件并说明替代关系。

本机编辑器使用会话令牌、来源检查和并发版本校验；下载按当前版本引用限制。静态 HTML 仅链接已保存附件，不显示虚假的上传成功。若需多人在线上传，必须另行提供有身份鉴权、权限和存储管理的服务，不能把本机编辑器开放到公网。

单文件上限 10MB，允许 PDF、PNG/JPEG、UTF-8 TXT/MD/CSV、无宏 DOCX/XLSX/PPTX；拒绝 HTML/SVG、脚本、压缩包、可执行文件及不匹配格式。格式检查不是病毒扫描，也不证明资料可信；敏感资料须获授权，公司如有要求应接入文件扫描。默认下载，不在线执行或预览附件。

上传落盘后构建失败会返回已保存及错误，不要重复上传；先修复并 build。若进程在文件落盘、引用登记之间中断，会留下未引用文件：Agent 核对 attachments 元数据、实际摘要与目标规划版本，恢复缺失引用后重新验证；不要删除或覆盖已有文件。

边界及异常用例维护在 `requirements[].boundary_cases`，功能详情以“特殊情况与处理”直接展示具体条件和预期；Markdown保留可读索引及独立补充，完整GWT仅导出一次。用例引用规则和验收，避免在其他章节复制正文。交付覆盖元数据见 [quality-contract.md](quality-contract.md)。

存在流程时按“模块全貌 → 必要子流程”组织，存在状态流转时提供对应状态图，图用 spec.diagrams 单一数据源生成，详见 [process-diagrams.md](process-diagrams.md)。原型静态状态展示不能替代状态流转图，文字流程不能替代应交付的图。

业务抽象按需说明“实体与关系 + 规则 + 状态机（存在流转时）”；状态机已有图则引用该图，规则只引用唯一数据源。无需抽象的功能不强加实体或状态，见 [business-modeling.md](business-modeling.md)。
