# 项目版本锁与交付准备

本文件只说明技能运行和交付管理，不把工具状态写进业务 PRD。

## 使用项目锁

`project.py init` 将版本、逐文件 SHA256、项目身份及 runtime 路径记入 `.skill-lock.json`，并保存该技能运行所需的说明、工具、模板、资源及场景输入。版本号相同但内容不同也算差异。普通维护和 new-version 使用锁内工具；入口脚本校验副本与根构建工具后路由，丢失或被改动则停止，不能静默改用已安装新版。

Agent 先读取锁，再按 runtime 加载对应 SKILL.md 和当前任务需要的 reference；小改仍走轻量维护。不要为版本锁重新加载全部说明。CLI 路由不能自动替代模型遵循对应说明。

无锁的现有 V2 项目仅允许只读检查；不能倒推技能来源。用户明确采用当前候选版本后执行升级，属于已有V2的运行工具更新，不转换旧契约。

## 显式升级

`project.py pin-status <项目>` 查看锁定/候选版本、指纹、完整性和差异文件。`upgrade-shell <项目>` 额外预览外壳、构建工具、规划资源和冻结资源差异，不写入。按用户升级意图执行 `upgrade-shell <项目> --apply`，先在临时副本构建并校验，通过且原项目未变才应用；覆盖前备份原锁和文件，保留旧技能副本。冻结/交接版本内容不升级。

副本失败不动原项目；原项目应用时的磁盘错误仍可能需要从 `.upgrade-backup/` 恢复，不宣称跨文件写入完全原子。升级后 Agent 在浏览器复核关键路径并重新登记证据，不能沿用旧指纹的结果。不要因局部修订顺便升级技能。

## 交付准备

1. 保留原始方案文件，按 delivery-review.md 对照输入、规则、验收和实际界面复核。缺少的语义/浏览器证据由 Agent 补做；业务取舍保持待确认，不为了就绪修改确认状态。
2. 构建、检查后启动/复用项目静态服务。运行 `prepare_delivery.py <项目> --url http://localhost:<端口> --input <原始输入> --evidence <证据.json> --out <项目外空目录>`；有自定义rubric时传 `--rubric`。命令复用 review_delivery 和 delivery_info，不另建规则台账。
3. 审查缺项输出 agent_todo；业务未决输出 business_decisions。默认未就绪只出报告；明确需要评审包才加 `--draft`。不要把待决问题改成已确认，也不要把脚本通过当作业务确认。
4. 就绪时静态包供下游阅读，源包保留当前源文件、全部版本、项目锁和运行副本、外部输入/复核证据；均有摘要清单。源包不包含Git及临时编辑/升级备份，不替代独立的Git仓库备份。不要发送给下游前未经核对的附件或历史资料。
5. 最终回复列localhost地址、本地Web入口绝对路径、完整项目目录、两份ZIP以及实际待决策（如有）。只生成报告不算已输出可交付ZIP；只出评审包不称已就绪。无需产品经理手动执行工具，不自动发送、部署或提交Git。

原始输入和证据副本保存在源包 `delivery-sources/`，索引记录来源；解压换目录后审查指纹可能变化，应重新审查。完整源包可用自己的 `build.py` 重建；静态包不含.py，也不具备持续维护所需的完整源数据。
