# 内容质量

输入是产品经理确定后的方案，不重新做痛点挖掘。完善只补齐本次方案必要的执行细节；无依据补充保持 ai-inferred/pending。

## 规则

- 一条规则一个约束，按条件、动作、结果表达；只写影响实现和验收的信息。
- 按业务选择输入校验、权限、状态变化、反馈、数据口径、失败恢复等维度；不机械穷举。
- requirement.module 是业务模块；rule_details.category 是规则分类。分类标题下使用短列表，不为每条细目重复小标题。
- 共用规则只写一次，状态只写差异。rule_details 存在时不用 rules 重复记录。
- 每个功能有可观察的验收；复杂规则配实例，简单规则不强造案例。
- 不编造指标、角色权限、时限、负责人、公司标准和技术契约。

## 边界与一致性

概览写清做什么、不做什么、对已有功能的影响。原文没有说明的重要边界标待确认。功能、原型、验收共用稳定 ID；画面与规则需人工核对。

## 测试与上线（仅在范围内时）

测试按前置、步骤、预期、关联规则编写；复用验收，不重复编一套业务口径。生成用例、原型检查和真实产品执行分别记录。上线条件只列实际依赖、负责人、验证与回退；未知项标待确认，不自动放行。

## 交付前复核

- 目录是否按业务分层，功能详情是否先说明功能再列规则？按 [functional-detail.md](functional-detail.md) 核对必要字段/内容、默认、操作结果、权限分支、异常恢复和验收；简单功能只检查适用项。
- 做与不做是否明确，补充和待决策是否可辨？重提是否区分原记录与本次操作，处理权限与查阅权限是否衔接，历史范围是否清楚？
- 搜索/排序、固定文案、指标数据来源等是否足以实现？每条规则的关键分支是否有可观察的验收，而非只有一条成功场景？
- 背景依据、用户价值与业务目标、关键场景是否清楚？现状、证据和决策理由是否有出处，假设是否被误写成事实？
- 成功指标与功能验收是否分开，指标口径是否只维护一份，上线后观察人群、窗口、比较依据和复盘责任是否明确或标待确认？
- 产品负责人、文档评审状态和研发进度是否区分？重要取舍是否仅记录已有决策，未编造备选方案？
- 是否有重复段落、空泛规则或为了模板添加的无关内容？
- 原型状态和必要元素是否齐全，清单中的元素是否位于对应画面？默认规则是否可读，异常状态是否只写差异？
- PRD 第一章本版功能清单是否明确，新增/修改/移除/沿用是否与基线一致？
- build/validate 与浏览器检查是否实际执行，有何未验证项？

交付时按 [quality-contract.md](quality-contract.md) 登记并检查：输入方案 → 功能 → 规则 → 画面/文字 → 验收。按功能类型检查适用维度，不适用有理由，待决策有问题和阻塞说明。`validate.py` 默认执行当前版覆盖检查；`audit_quality.py --strict --report` 输出可读报告。脚手架结构通过不代表交付完整。

关键边界与异常用例在功能详情中折叠展示，导出保留表格。数值上下界用文字即可；布局、元素、可操作性、反馈位置或恢复路径变化时补状态画面。检查登记关系后仍需语义复核，不能以“不适用”或“文字表达”绕过必要内容。
