# 验收执行与上线复盘

用户提供实际执行结果、上线观测或要求记录/修订结果时使用。固定入口 `#/v/<版本>/_outcomes/results` 展示验收、指标及转入本版的跟进事项。已冻结版本仍可追加事后记录：它们存放在项目根 `outcomes/`，不是版本 content 的一部分；界面必须明确是持续更新的台账，不冒充冻结时已经存在的证据。

## 正式保存

浏览器“填写结果草稿”可选择类型、编辑 JSON 并导出；这是未入库草稿，刷新/离开不保证保留。用户也可口述结果，由 Agent 按下列字段整理文件并保存。真实结果不足时记录 not_run/inconclusive 或询问，不编造执行人、时间、证据或数字。

```bash
python3 <skill>/scripts/record_outcome.py <项目目录> <结果JSON文件>
python3 <skill>/scripts/project.py build <项目目录>
python3 <skill>/scripts/validate.py <项目目录>
```

先确认结果的具体版本/交接修订、环境、产品构建。保存命令校验关联、追加 UUID 文件、记录当时物料指纹与验收文本。随后构建更新外壳；构建失败不代表记录未保存，保留记录修复后重建，勿重复入库。重建后，本版「页面需求与验收」的验收条目会显示最近一次验证记录（结果、范围、时间与基线漂移标记）；徽标取自台账，有记录不代表当前仍通过。不自动发布、改版本状态或创建下一版，不操作外部系统。

普通规划版内容变化会将既有结果标为“基线已变化，需复核”；旧记录仍保留当时验收文本。基线相同只表示物料指纹相同，不能证明实际产品构建一致。范围 prototype 和 product 分开筛选，各自展示当前基线未登记执行的验收项；有记录（包括失败、阻塞）不代表通过。不跨环境或不同构建聚合成全量通过率。

## 验收记录字段

```json
{
  "kind":"execution", "version":"v1.1.r1",
  "requirement_id":"FR-ORDER-001", "acceptance_id":"AC-ORDER-001",
  "scope":"product", "result":"not_run",
  "environment":"待提供真实测试环境", "build":"待提供产品构建号",
  "actor":"记录人姓名/工具", "observed_at":"2026-09-09T12:00:00+08:00",
  "evidence":[], "notes":"尚未执行；这只是填写格式示例"
}
```

scope：prototype（原型验证）/product（真实产品验收）；result：passed/failed/blocked/not_run。非 not_run 必须填写 evidence 数组，包含测试报告、截图、工单或日志的定位和必要说明；避免敏感日志、密钥及私人信息。工具只保存文字引用，不上传文件、不访问链接，也不独立核验真实性。观察时间需要时区；记录入库时间另行生成，不能混淆。

## 指标观测字段

kind=measurement，公共字段 version/actor/observed_at/evidence/notes 相同，额外必填文本：

- goal：对应上线目标；metric：口径、公式、单位、去重与适用人群。
- baseline/target/actual：基线、目标、实际；未知明确待补，不填造假的零。
- window：观察起止、时区及样本范围；data_source：数据来源或报表定位。
- decision：met/missed/inconclusive，由有证据的分析填写，不按字符串自动计算达标。

没有基线、样本不足、口径发生变化时使用 inconclusive。即便指标上涨也不能直接归因于功能；必要时注明实验、季节性及样本限制。上线计划里的暂停/回滚条件由负责人评估，台账不自动执行暂停、回滚或外部通知。

## 更正与下一版跟进

更正已有记录时提交完整新记录，并带 `supersedes: "旧记录ID"`；须为同版本、同范围及同一验收/指标对象，不能重复更正已经有后继的记录。旧记录保留并标记已更正。错挂版本或对象时不能靠更改身份覆盖旧记录；在旧对象追加说明更正，并对正确对象另行登记。

需要在下一版处理时，记录可带：

```json
{"follow_up":{"target_version":"v1.2","owner":"具体负责人或待认领","action":"补充失败重试策略，评审后决定是否纳入"}}
```

目标必须是已存在的其他 planning 版本；不存在时先提出下一步规划建议，只有用户同意创建版本才执行。目标版的结果页自动显示此来源及行动，不自动生成 confirmed 需求。开始规划该版本时读取转入事项，核对是否已处理、是否真实需求、范围和责任，再按正式需求变更流程纳入 spec，并在 notes 记录关联 FR/处理决定。旧跟进记录是来源证据，不等于事项已实施；暂不提供多人实时协作或外部工单同步。

台账与项目一起备份。CLI 只追加、不提供覆盖或删除；本地文件仍可能被人工修改，不是防篡改审计系统。记录、编辑、构建应串行运行；不要在多个进程同时修改项目。冻结物料和已有用户项目不会自动升级，只有用户要求使用新功能时按既有升级流程更新工作区外壳与工具。
