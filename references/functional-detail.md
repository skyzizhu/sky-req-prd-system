# 功能详情的交付结构

生成或完善第三章时读取。目标是让开发确定行为、测试确定预期；PRD 本身能表达业务要求，原型、原输入和流程图不能承担遗漏的规则。保持“业务模块 → 功能”的层级，不增加顶级菜单。

## 按适用性组织

| 层次 | 应回答的问题 | 合适表达 |
| --- | --- | --- |
| 功能说明 | 为谁解决什么任务，本功能做到哪里 | 简短说明，不复制背景和全局范围 |
| 入口与前提 | 从哪进入、谁能用、依赖哪些既有能力，直接访问不满足条件时如何处理 | 短规则或引用共用前提 |
| 数据与字段 / 内容与展示 | 需要哪些业务内容，来源、必填/可编辑、默认、单位、格式、空值是什么 | 字段/内容表；约束引用唯一规则，避免抄表再抄一遍正文 |
| 操作与结果 | 用户触发什么操作、系统做什么、成功后数据/状态/反馈/去向是什么 | 条件 → 动作 → 结果；复杂分支用表格 |
| 分类规则与适用图 | 输入、权限、计算、状态及分支如何约束行为 | 只列适用分类；有真实流程/流转才画图 |
| 异常与恢复 | 失败、未知结果、冲突、无权限、离开/重入如何处理；什么保留、何时可重试 | 异常条件 → 当前结果 → 恢复行为，不写“按系统处理” |
| 边界用例与验收 | 哪些代表性输入/分支能证明结果正确 | 已有 boundary_cases 与 GWT，涵盖关键正常、边界和异常分支 |

简单展示可以只有一段内容及验收；表单、审批、查询等按实际复杂度展开。不强制每个功能使用全部标题，也不因模板要求引入新的业务功能。

## 各类型易漏内容

涉及字段和控件时，同时按 [control-annotations.md](control-annotations.md) 核对选项、默认值、约束及交互结果；内容仍写入本章的唯一规则源，由原型引用，不再另抄一套控件说明。

- **表单**：字段含义/来源/默认值、必填与校验时机、数值精度与空白处理；动态行初始数量、增删及上下限；成功去向；取消/离开后的数据去向。已有共用输入约定可引用，不机械列全部字符类型。
- **列表和详情**：可见字段、内容分组及操作条件；搜索匹配和触发方式、筛选选项和默认值、排序字段的业务含义、分页和返回定位；空数据与失败区分。详情可归入已有功能说明，不必虚构一个独立业务功能。
- **审批/流程**：谁有权处理与谁有权查阅分开；处理完成或状态变化后如何反馈和返回；审批人来源、多人归属、可用性、实际会发生的组织变动。已有组织规则可引用，不能自动增加代理、转交或配置能力。
- **修改/重提**：原记录和本次操作分开；新建成功查“已创建”，重提成功查“本次修改/轮次已生效”。失败不生效、处理中和未知结果分别表达；旧业务数据、历史及本次未提交内容如何保留。按适用性明确刷新/重入和幂等恢复，不把技术标识的具体实现交给产品设计。
- **固定内容**：给出可交付文案或唯一内容引用；“有说明页”不等于内容已确定。
- **数据与指标（第四章）**：定义、分子分母、对象/单位、统计时间、去重和排除项、空值/未知/迟到结果、数据来源；实施范围包含采集时写事件字段类型、必填及枚举。没有数据来源的公式不算闭合，也不自动扩展埋点/报表范围。
- **非功能（第五章）**：适用场景、实际基线或可验证目标及验证方式。产品明确业务结果，技术方可提出技术阈值；“遵循公司规范”须有真实依据，未知项列具体问题。

## 唯一来源与展示

网页按“业务模块 → 功能 → 规则分类 → 规则主题”展示。模块标题、功能标题、规则分类与规则主题需有明确视觉层级。功能头部集中展示标题、次要元信息与修改入口，下方简短功能说明与规则正文分隔；宽屏分类标签与规则正文分栏，窄屏转为分类标题在上。规则正文保持白底、轻分隔，避免层层底色块和多个同级标题争抢注意力。规则主题下直接显示约束与表格，编号在规则标题旁弱化展示便于定位，依据与验收关联放末尾折叠。关键规则不默认折叠。左侧“功能需求与规则”的强调星标放在文字后。

规则的关联验收编号在网页中可直接跳转到本版本、本功能的具体验收，并展开内容；保持唯一正文，不让读者复制编号重新搜索。未确认的示意值与正式业务预期分开，不能因画面有值就写成已确定验收条件。

新规则提供可定位的简短 `title`（例如“活动类型筛选”“默认排序与分页”）。`statement` 表达一个完整的简单约束；同一主题包含多个可独立执行的条件或行为时，用一句作用说明加结构化分项，执行细节放可选 `clauses: [{label,text}]`，如“可选范围”“默认值”“触发与联动”“空值与异常”。简单规则仍可一句话；多项约束不挤成分号长段，不在摘要逐项重复 clauses 或 table 的内容。改写既有长段时先逐项核对取值、默认、时机、联动、异常与恢复，不能靠自动切句改变含义。

表格适用于字段定义、选项映射和条件分支。成功、失败、冲突或未知等结果需要横向比较时，用“条件 / 系统处理 / 界面反馈 / 后续操作”决策表替代对应长段，保留副作用与允许重试的前提；没有的分支不编造。不要把所有规则机械做成巨表。一个规则主题如果同时包含独立的排序、余量计算、分页等，应按读者任务拆为不同规则，重新关联原型和验收；不要靠标点自动切句或根据渲染器猜业务含义。既有未结构化正文保持原意，展示层不自动改写。

`title` 和 `clauses` 与 statement/table 同存在唯一 rule_details 内，PRD网页、Markdown导出和原型说明读取同一份数据。clauses的label/text非空；中文标签按本次含义命名，不预填不适用行。未知项继续明确待确认。

功能规则继续保存在 `requirements[].rule_details`。可选 category：`entry/fields/display/behavior/validation/permission/state/data/feedback/recovery/content`，也允许业务自定义分类。网页和完整导出按上述顺序显示实际有内容的分类。不要另建一套重复规则章节。

需要字段表、内容表或决策表时，使用规则可选的 `table`；statement 概述表的作用，表内维护细节，不在 statement 逐格重复。来源/确认状态沿用所属规则；不同来源或确认状态的行应拆成不同规则表。精确业务约束可在表内引用已有 RULE 编号，不复制其全文。

```json
{"id":"RULE-FIELDS","title":"名称字段","category":"fields","statement":"字段来源及编辑性如下。","clauses":[{"label":"校验约束","text":"引用 RULE-NAME，不在本表重复长度限制。"}],"source":"ai-inferred","status":"pending","table":{"columns":["字段","来源 / 默认","编辑性"],"rows":[["名称","新建为空，修改带入当前值","可编辑"]]},"acceptance_ids":["AC-FIELDS"],"presentation":{"mode":"text","reason":"文字表格足以表达字段定义"}}
```

待明确的实现口径用已有 `review.checks` 的 `pending/question/blocking` 登记，在功能正文与导出中直接展示。问题写成可以回答的业务选择及影响；已知部分仍写完整。阻塞事项如实标 blocking，不为质量报告通过而降级。未经确认的补充规则标 ai-inferred/pending，不能把默认建议写成用户决定。

## 共用归属与操作查阅

规则正文始终归属于一个实际负责该行为的功能。跨功能适用时，其他功能通过可选 `shared_rule_ids: ["RULE-…"]` 显示带所属功能的共用引用，不复制正文、不虚构“共用功能”凑归属；不把填写返回/草稿规则藏在仅负责列表查询的功能里。范围确属模块共用时，在最贴近该行为的既有功能维护，并在所有适用功能引用。

具体操作需要组合校验、权限、处理中、结果及恢复时，用该操作规则的可选 `related_rule_ids: ["RULE-…"]` 指向必要规则，读者可沿操作查完整行为，不把整个功能所有规则都绑过来。两个字段只保存本版本规则ID，无正文；校验拒绝缺失、重复及自身引用。关联不是继承或新规则，也不消除被引用规则的待确认或阻塞状态；需核对其对当前功能的影响。原型仍显式绑定当前控件/状态所需的规则，不能靠关系推定已覆盖。网页提供精确定位、返回来源和命中规则高亮；Markdown导出保留共用与关联引用。

业务正文只写真实产品要求：控件、数据、触发、反馈、状态和恢复。原型画板的排列、标注查看、合成时钟和样例身份等放生成规范或附录，不混入业务执行规则；线框示意尺寸与真实产品兼容/触控要求要区分。

## 内容复核

逐项对照原输入中的独立约束，而非仅关联整段摘要；逐条检查规则引用的验收是否覆盖其关键分支。实体表或图里独有的执行约束要归入规则，其他位置引用。空泛的“支持、保留历史、失败可重试、按权限”必须补足对象、条件及结果。去重不能删掉独有信息；共用行为有准确引用即可。

复核时以一次完整操作为线索，从入口/前提走到校验、触发、处理中、结果及恢复，检查规则关联能否串起行为。对涉及时间或可变数据的功能，按实际情况核对跨日、等待后过期、草稿恢复后失效、并发变化等；缺少业务取舍时登记具体待确认问题，不自行决定清空/保留/改期。验收关联需覆盖这些实际存在的分支，不为凑场景强加新功能。

自动检查表结构、引用与检查项状态；它无法证明表格写全、问题已回答或预期正确。最终仍需按本节做语义复核。PRD 允许待评审稿，但关键实现问题未解决时不得把登记覆盖通过说成最终交付已就绪。

## 交付闭合

逐项核对输入中的独立约束，而不只登记整段摘要：对象/范围、条件、取值/默认、触发、成功结果、适用的失败/未知/恢复和验收结果都需有明确去向。核对数据写在 quality.input_items.constraints，规则正文仍只在 rule_details。关键字面值可作防遗漏检查，不能代替语义核对。

规则、表格、分项各承担新增信息：摘要说明作用，表格维护枚举/默认/映射，分项只补充校验或联动。不逐格复述表格；保存顺序、展示顺序和勾选顺序不同的，明确最终口径。术语及依赖名称对照当前方案，不继承其他案例的业务词。

未决问题明确影响实现、验收还是仅文案校对。前两者标 blocking:true，并说明受影响功能；纯文案不改变含义/约束时可标 editorial、不阻塞。不以“可以继续出评审稿”代替“可以实现”。幂等与未知恢复说明同一次/新一次操作的业务边界、可观察结果及必要处置责任；标识生成、轮询实现等由技术契约确定，不擅自增加超时自动取消等功能。

同一场景按 quality-contract.md 的引用型边界用例维护；输入、预期不同才作为独有补充。核对 GWT 是否真的覆盖关联规则的关键分支，尤其区分空结果、失败、结果未知和恢复，不能只检查 ID 存在。
