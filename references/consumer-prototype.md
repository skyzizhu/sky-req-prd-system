# C端与移动端原型

C端是受众，mobile/h5/miniapp/web是平台。消费类桌面Web仍按桌面任务布局；B端移动应用同样需要移动画板。先读已确定的平台、视口和既有设计约束，不能仅因audience=c就画手机、加登录或支付。影响布局的端未明确时澄清；兼容范围未知保持待确认。

## 按端绘制

- 移动画面在桌面阅读器中也保持手机内容宽度；普通Web不套手机框。使用实际项目尺寸；缺省可用390px逻辑宽度作示意并标明，复查320px和390px。不添加装饰手机外壳，不缩小文字来塞控件。
- 移动字段、按钮和点选标签用可触控尺寸；共享样式默认44px操作高度、16px输入文字，仅是可调整的原型默认值，不声称满足所有设备规范。单选/复选按真实形态，标签扩大操作范围；编号仍放独立栏，不能盖住控件。
- 导航、返回、主要操作、底部栏及表单错误按实际任务呈现。长内容默认在交付画板完整展开并由阅读器滚动；底部操作区展示在独立页内，不position:fixed到整个阅读器，不能遮住下一张画板。实际产品固定/吸底、返回及滚动规则在对应标注说明；确需演示局部滚动时另外验证编号随滚动定位及内容不被裁切。
- 移动底部操作区留必要间距，并预留设备安全区。手机顶部系统栏、小程序导航区等仅在影响可用空间时示意；不能把阅读器顶部工具栏当产品导航。
- 同一详情中的页面、弹窗、底部操作面板/抽屉仍按prototype.md上下独立画板，各有标题、白色容器、触发说明。底部面板保留其底部出场含义，不能因拆画板误画成普通正文。

共享runtime.css支持显式标记，不自动改变已有B端页面：

```html
<section class="sr-artboard" data-ps-surface="page" data-ps-platform="mobile">
  <h3 class="sr-artboard-title">移动端 · 信息填写</h3>
  <div class="sr-artboard-body"><!-- 真实字段、错误及精确标注 --></div>
  <div class="sr-mobile-actions"><!-- 本页主操作；其固定方式见规则 --></div>
</section>
```

单画布可在.sr-snapshot标data-ps-platform="mobile"；多个画板则各标在.sr-artboard，勿把整组画板限宽成手机内容。每个画板的sr-artboard-body仍需存在；操作区属于该画板，不能脱离其容器。自定义宽度/尺寸在页面CSS中按已确定平台覆盖。

## 按本次任务检查状态与规则

沿用local-controls.md及control-annotations.md，不重复维护字段契约。额外关注移动任务中适用的中断：返回/退出是否保留输入，登录态失效或授权拒绝后如何恢复，重复点击、弱网失败/未知如何区分，以及外部跳转返回后的结果核实。只纳入实际涉及的场景；无支付、上传、定位或登录流程时不添加这些模块。

软键盘涉及的字段按真实type/inputmode/autocomplete等属性表达；有格式化、校验时机、金额/数量或协议选择时明确具体规则，未确定的阈值和取舍待决策。输入法、键盘弹出遮挡、系统返回/授权和外部App跳转不是静态HTML可证明的功能；可画对应状态并写规则，不模拟系统能力或声称真机已通过。

## 实际验证

分别验证“桌面查看移动画板”和“触屏窄视口查看交付物”；检查内容宽度、触控标签、长文案/错误、底部区与安全区、原生选择/输入以及编号不重叠。状态覆盖从原始方案反查，不以通用模板凑数量。多画板检查各自标题/间隔、字段保留和触发关系。

浏览器触屏模拟可以证明局部控件与布局路径；真机键盘、安全区实际值、原生小程序/系统控件、真实弱网和业务请求未测就明确未验证。C端不默认高保真，仍以状态、元素和规则完整的线框交付。

## 平台与移动任务的闭环

平台先确定App（适用iOS/Android）、H5或具体小程序宿主；沿用业务已确定的宿主/版本约束，未知写待决策。按实际能力选择适用项：

| 场景 | 必须明确的结果，不默认新增功能 |
| --- | --- |
| App | 页面返回/系统返回的差异、切后台再回到前台、进程终止重开时保留什么；只在涉及系统授权/外部应用时写其返回路径 |
| H5 | 浏览器返回/刷新、直接链接进入缺少上文、离开重入；宿主WebView与外部浏览器有业务差异时单独说明 |
| 小程序 | 页面返回、关闭后再进入、宿主授权/登录恢复；依赖宿主能力时说明平台及失败后的替代入口，不捏造原生接口行为 |

导航规则写清：入口→目标页→携带/保留数据→返回落点与滚动/筛选恢复。中断规则写清：发生阶段→已知业务结果→保留数据→重入画面→允许的恢复动作。系统授权按首次未询问、允许、拒绝/受限以及设置后返回等实际适用分支表达；没有调用系统能力就注明不适用，不能为检查而增加授权流程。

提交前/处理中/结果未知的返回、中断应分别检查；未知结果回到前台仍先核实原操作，不因页面重建再创建。是否允许退出、是否保存草稿和保存期限由方案决定，缺失且影响实施则阻塞待决策。列表加载更多/到底、刷新、过期或不可用内容，仅在原功能涉及时补齐。

## 移动组件的画板表达

产品导航栏（返回/标题/本页操作）、底部导航（项目、当前项、切换结果）、固定主操作区、选择面板、Action Sheet/底部弹层和系统授权提示，按实际方案绘制并逐控件标注。原生系统界面以“系统界面示意”命名，不把它误作新增业务页面；无需实现真实系统交互。

底部弹层在独立画板中保留标题、选择项/默认、取消/确认/关闭及结果说明，并用“实际从底部出现”等简短说明保留定位含义。返回保留、输入错误、授权拒绝、内容失效、加载失败、处理中/未知/核实后的恢复，只要改变必要元素或操作，就需对应画面；不为相同布局的每个数值造画板。

## 检查登记

quality.mobile_review只引用唯一业务规则及其验收，不在台账复制规则正文。移动App/H5/miniapp项目必须登记以下六维；非移动项目不强加此登记：

```json
{"dimension":"navigation","status":"covered","rule_ids":["RULE-BACK"],"acceptance_ids":["AC-BACK"]}
```

维度：platform（平台/范围）、navigation（入口与返回）、interruption（中断重入）、authorization（系统授权）、network（网络与结果恢复）、components（移动组件与状态）。covered需有效规则和对应验收；not_applicable需本次具体理由，platform不能跳过；pending需question、impact及blocking，影响实现/验收时不能标不阻塞。规则仍写第三章，台账不增加PRD菜单。

统一审查的mobile_delivery需按上述六维给出可定位证据；自动引用通过不能证明移动需求没有遗漏。完整移动场景须从原始方案生成标准PRD、跨页关系、移动画板及规则，而非用电话/密码表单或触屏模拟替代。
