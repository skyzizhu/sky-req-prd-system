# 模块流程、子流程与状态流转

编写 PRD 流程章节或有复杂流程/状态的功能时读取。图的用途是让开发和测试理解路径、分支、恢复与交接；已有方案有图时先核对补全，不直接照搬失效节点。

## 放在哪里、何时展开

- 先判断模块是否确有业务流程：有才在第二章“用户与业务流程”提供整体流程图，说明入口、角色/关键动作、正常及异常分支、结果及跨模块交接；没有则不画。已有能力和本次范围外的连接点注明身份，不把连接点当新增功能。大模块可有多张有明确范围的总览图。
- 第三章对应功能详情：确有子流程时再展开；模块图中的复杂节点涉及多步处理、条件分支、跨角色协作、异步结果、失败重试或独立子模块时，展开子流程图。存在上层图时关联具体节点；独立流程/状态图无需为了层级虚构父图。必要时继续分层，不能循环引用。
- 当对象或页面存在多个影响行为的状态时，补状态流转图，写清初始状态、可达状态、动作/触发条件、成功/失败、回退/重试、结束或交接。状态图说明“怎么变化”，静态原型说明“变化后看到什么”，两者都需要时分别交付。
- 业务对象状态与页面交互状态分开命名。例如“订单待支付/已支付”与“创建页默认/提交中/失败”不能混为同一状态机。
- 简单单步功能无需强造子流程；没有状态变化也无需强造状态图。在 diagram_review 中说明理由；已有规则明确涉及流转或状态时不能填不适用逃避画图。未知分支标待确认，不默认为成功、不编造审批/支付/取消等范围外功能。

图上保留动作、条件、状态名及结果；长度、精度等细节留在规则/边界表。复杂图优先拆层，避免一张图把所有字段和规则编号塞满。正常路径和本次涉及的异常路径都要表达：校验不通过、无权限、业务拒绝、请求失败、超时、冲突、取消、回退或重试等仅在真实适用时纳入，不能照清单编造。所有已确定分支都应有去向，失败不能断头，重试必须回到明确步骤；未知去向登记待决策。总图可概括异常并指向子图，细节不必重复。不能重复执行的操作可画自环并注明“不触发请求”等结果。

## 画法与语义

- 流程图从上到下安排主路径。步骤用矩形，条件判断用菱形，开始/结束用圆角终止符，已展开的子流程可用双边框。节点可声明 `type: process/decision/start/end/subprocess`；开始节点同时 entry=true，结束节点同时 terminal=true。已有节点未声明type时保留步骤矩形，不由渲染器猜测业务含义。
- 判断节点写一个可回答的问题，例如“校验通过？”，出口写“是/否”或明确且互斥的枚举结果；全部已确定情况必须有出口。不要把多个条件、重试动作和副作用挤进一个节点或一条箭头。不把异步结果未知直接并入明确失败。
- 节点名称描述动作或状态，简短且无歧义；同一图不要用相同名称代表不同对象。模块图体现跨功能的主路径与异常交接，子图只展开选中的节点，不重复整个模块图。复杂路径应按职责或阶段拆图，保持上下层对应。
- 状态图节点只写同一对象或同一页面的状态。迁移依次说明触发、必要条件、目标状态及副作用；可用 `edges[].condition`、`effect` 单列条件和结果，label写短触发。状态不变不等于“成功”：自环只有实际存在触发/处理时才画；禁止操作可直接在规则说明，不为凑图画假迁移。
- 初始标记说明实例进入哪个状态，不代表每次打开页面重新创建实例。终态只表示本图确实终止；持续运行对象不强画结束。失败/禁止/未知分别核对是否改变业务状态；页面反馈与业务状态机分开。

## 可读尺寸与迁移说明

图中状态迁移统一用 T01、T02 等局部编号，图下自动生成唯一来源的迁移说明表，完整呈现起止状态、触发/条件、结果及规则引用；编号不是规则ID，不跨图引用。流程图的短分支标签直接展示，过长连线自动使用同样编号并生成说明表，全文不截断、不省略。

长条件应优先拆为真实判断步骤或填入condition/effect，不能只缩成无含义的“满足条件”。编号表能避免长字重叠，但不代替路径语义复核。图和表是同一diagrams数据的两种投影，不手工另写迁移表。

网页按原始可读尺寸显示SVG，不强行缩成容器宽度；超出范围可横/纵滚动并用缩放按钮查看。缩小用于总览，100%用于读字。渲染等待字体就绪，流程标签采用SVG文本，避免HTML标签的行高与裁切问题。Markdown导出的图源和迁移说明保留同一内容，导出端的布局仍需支持Mermaid。

## 单一来源

`spec.json` 顶层 `diagrams[]` 是图的唯一源；生成器自动编译 Mermaid。模块图编入第二章，子图编入对应功能和完整 Markdown 导出；不要在 users.md 或其他文档手工复制第二份相同图。

```json
{
  "id":"FLOW-CREATE",
  "title":"创建订单 · 子流程",
  "module":"订单管理",
  "kind":"flow",
  "level":"detail",
  "requirement_id":"FR-ORDER-001",
  "parent_id":"FLOW-ORDER",
  "parent_node":"create",
  "source":"origin",
  "status":"confirmed",
  "nodes":[
    {"id":"edit","label":"填写订单","entry":true},
    {"id":"done","label":"创建成功并返回列表","terminal":true}
  ],
  "edges":[{"from":"edit","to":"done","label":"信息有效且请求成功","rule_ids":["RULE-ORDER-SUCCESS"]}]
}
```

上例只展示结构；实际子流程仍需补齐本次适用分支。

- kind 为 flow 或 state；level 为 module 或 detail。模块图可以是 flow 或 state，不强制两者同时存在；无 parent。功能图关联 requirement_id；确有上层图时才填 parent_id/parent_node。节点 ID 在图内唯一。
- 模块图中功能节点通过 requirement_ids 关联本模块功能，例如 `{"id":"create","label":"创建订单","requirement_ids":["FR-ORDER-001"]}`。仅实际参与流程的功能需要映射，不把纯展示或无流程的功能强行串入。
- nodes 中 entry 指明入口或初始状态。流程图用 terminal 指明本次范围的结果/交接节点；状态机不一定有终态，持续运行的状态循环不强制 terminal，也不因此补造结束状态。
- edges 必须写动作/条件 label，可用 condition/effect 补充非空条件与结果说明、rule_ids 引用已有规则。分支含互斥条件，异常含恢复去向；入口可达性检查不能代替业务路径完整性复核。
- 页面交互状态可在节点加 `prototype:{"page":"create-order","state":"failed"}`，对应静态画面需存在。纯业务状态没有页面时不强制关联原型。
- 图保留来源和确认状态；AI 补充仍待确认。图确认不能把关联规则自动改为已确认。

在 `quality.module_reviews[]` 记录模块流程适用性；不是“每个模块都必须画图”：

```json
[{"module":"内容展示", "flow":{"status":"not_applicable","reason":"仅展示静态说明，无业务处理流程"}}]
```

存在流程时使用 `flow:{"status":"covered","diagram_ids":["FLOW-ORDER"],"requirement_ids":["FR-ORDER-001"]}`，requirement_ids 仅列实际参与流程的功能。范围未确定时使用 pending/question/blocking；不以等待确认的名义编出一张图。模块没有流程但某对象有状态流转，可以只提供其状态图。

每个功能登记是否需要子流程与状态图：

```json
"diagram_review": {
  "flow":{"status":"covered","diagram_ids":["FLOW-CREATE"]},
  "state":{"status":"not_applicable","reason":"只读静态内容，无状态变化"}
}
```

covered 需有本功能、同类型的图；not_applicable 需有理由；pending 需有 question 和 blocking，处理方式同质量契约。需要两类图时分别关联，不能用子流程图冒充状态图。

## 交付复核

- 有流程/状态才画图，是否误把没有的能力补成图？适用模块图是否覆盖实际参与功能和真实交接？子图是否展开正确的上层节点？
- 所有已确定分支、触发条件、失败恢复和禁用操作是否清楚？图和规则矛盾时先修正数据源。
- 状态名、流转条件、原型画面及验收是否一致？纯后台状态不强造页面。
- 从入口逐条走完正常、拒绝、明确失败、未知、重试/退出，核对每条箭头的条件与规则、验收一致；自动检查无法证明互斥与穷尽。
- build/validate/audit 后实际在浏览器确认图形渲染；不能只看到 Mermaid 源码就宣称图已交付。站点随包携带固定版本的本地 Mermaid，在文档初始化前按 defer 顺序加载；不依赖CDN或固定等待时长。缺资源与图源错误分别提示，并保留源代码；需要修复或说明未完成的验证。

浏览器复核还需在100%下检查全部节点及连线文字，无截断、重叠或被容器裁切；分别检查模块图和子图、桌面与窄屏、缩放恢复及键盘滚动。大图有滚动不等于缺失；只看缩略图不能声称文字可读。

自动检查覆盖节点类型、判断节点出口数量/重复标签、结束点继续流出路径、缺图、失效上下层关联、节点/连线引用、入口可达性及原型状态引用；它不证明所有业务分支已经被登记。Markdown 导出保留可编辑 Mermaid 图源，查看端需支持 Mermaid 才显示图形。

## 场景驱动的分支复核

先从原输入和关联GWT列出本图适用的结果，再画路径；不能从现有箭头反推“已经完整”。从每个真实操作逐条走正常结果、校验拒绝、明确失败、未知及恢复：恢复后重新校验是否仍可能失败？重试回到哪一步？什么保留、何时可新建？只核对本次实际存在的情况，无依据的分支记待决策，不补造业务。

为新图连线赋稳定 `edges[].id`，在 `path_reviews` 引用同模块的规范验收与有序连线，不复制GWT：

```json
{"id":"PATH-RETRY-INVALID","acceptance_ids":["AC-RETRY-INVALID"],"edge_ids":["E-RETRY","E-INVALID"]}
```

这条路径可从失败状态开始，无需每次从全图入口重走。验收的given/when/then须真正说明本路径的前提、触发和结果；必要时先补遗漏的独立GWT，再补图。编号只用于追溯，之后增删连线不重编号。路径核对只存检查证据，不向PRD添加第二份迁移正文。

检查器校验连线ID、路径连续性、验收及规则关联，删掉已登记的重试分支也会报错，即使图仍连通。未登记路径标待复核，不视为完整；未交付验收时可省acceptance_ids。它仍不能发现图和路径清单同时遗漏的业务分支，也不能证明分支互斥、条件正确或副作用齐全；最终由Agent对原始输入逐场景复核，并实际查看图形。没有图的功能不强制登记路径。
