# sky-req-prd-system

把产品经理已经确定的产品方案，整理为可评审、可实施、可验收的 PRD 与多状态线框原型，并在同一个 Web 中持续维护各版本物料。

目标是减少产品经理与开发、测试、设计之间的反复沟通：规则、范围、边界和状态交代全面，表达简明，关键要求无需下游猜测。输入可以零散，但应当是经过产品分析后的方案。

当前发布：[`v2.0.0-preview.34`](https://github.com/skyzizhu/sky-req-prd-system/tree/v2.0.0-preview.34)。可用于实际需求的整理与交付，版本标识仍为预发布；建议固定发布标签，按真实方案确认业务规则后交付实施。

## 解决什么问题

| 常见问题 | 本技能的处理方式 |
| --- | --- |
| 方案已确定，但需求描述零散 | 按标准 PRD 组织，先说明背景目标、功能清单和范围，再展开功能细节 |
| 规则省略条件、异常或边界，开发需要反复询问 | 补充影响实现的前提、字段、操作、结果、限制、异常恢复与验收；无依据的取舍标待确认 |
| PRD、原型和测试各写一套规则，后续互相矛盾 | 规则与验收使用统一来源，原型按当前控件和状态引用，其他材料链接原文 |
| 只有默认页面，设计与测试不知道其他状态怎么处理 | 覆盖实际需要的加载、空、校验、失败、权限、结果等画面，以及必要的局部控件交互 |
| 修改一点就重新生成，覆盖手工调整 | 按规则、控件、页面或文档片段做增量维护，并检查必要关联 |
| 新版本另建 Web，历史材料难找 | 同项目固定入口，左侧按版本分组，各版保留自己的完整物料 |

## 适用范围

- **使用者**：产品经理；主要下游为开发、测试、设计，技术负责人可通过目标、功能清单、边界和风险查看整体方案。
- **输入**：已确定的产品方案、功能调整、明确的页面与规则；支持首次生成、局部维护、新版迭代和交付审查。
- **平台**：支持 B 端和 C 端，按实际产品平台生成 PC Web、移动 Web、App 等原型。移动端支持指需求和画面的移动交互，例如底部操作区、弹层、键盘影响与平台返回行为，按方案适用性处理。
- **交付选择**：可生成整套材料，也可只要求 PRD、原型、流程或测试材料。仅原型仍保留它所依赖的最小规则数据。

本技能不负责从原始吐槽中判断需求是否成立，不自动实现业务后端，也不把原型当作正式视觉设计稿。原型中的简单选择、展开与开关可操作，业务提交、网络请求和真实推送不做模拟实现。

## 安装与更新

### 通过 Codex 安装

在 Codex 中输入：

```text
请安装这个仓库根目录中的 skill，固定到标签 v2.0.0-preview.34：
https://github.com/skyzizhu/sky-req-prd-system
技能名称为 sky-req-prd-system。
```

安装后的技能目录应直接包含 `SKILL.md`、`scripts/`、`references/` 和 `template/`。安装完成后，在后续对话中调用；未出现在技能列表时重新打开会话。

### 手动安装

需要 Git 和 Python 3。以下命令适用于目标目录尚不存在的情况：

```bash
mkdir -p "${CODEX_HOME:-$HOME/.codex}/skills"
git clone --branch v2.0.0-preview.34 --depth 1 \
  https://github.com/skyzizhu/sky-req-prd-system.git \
  "${CODEX_HOME:-$HOME/.codex}/skills/sky-req-prd-system"
```

不要把第二份同名技能放进其他会被扫描的技能目录。若已经安装，先确定现有安装位置，避免实际调用到旧副本。

上面的命令固定安装此发布版本，Git 显示 detached HEAD 属正常情况。希望跟随开发分支的维护者可省略 `--branch` 和 `--depth`；日常使用建议固定标签。

### 更新

可以让 Agent 执行：

```text
请检查 sky-req-prd-system 的实际安装位置和本地改动，保留本地修改，
将本机技能更新到发布标签 v2.0.0-preview.34，避免重复安装。
```

跟随 `main` 分支的 Git 安装且工作区干净时，可执行 `git pull --ff-only`。固定标签的安装需获取并切换到明确的目标标签；下载式安装由 Agent 核对并替换文件。切换前保留本地修改，不把 `git pull` 用于固定标签的安装。

**更新技能不会自动改写已生成项目。** 已有项目需要新版阅读器或原型运行资源时，明确要求升级项目外壳，再核对受影响页面；版本内容与历史快照有独立保护。技能版本与产品项目的 `v1.0`、`v2.0` 是两回事。

## 首次使用

### 输入什么

说明方案、产品平台和所需交付物。尽量提供会影响结果的信息：

- 本次增加或改变哪些功能，哪些不做，依赖哪些已有能力。
- 使用角色、入口、字段、选项、默认值、权限、业务规则。
- 正常结果、必要异常及恢复方式；已确定的验收条件。

不必先整理成完整 PRD。缺少关键业务取舍时 Agent 会询问；必要补充会区分已提供内容和 AI 推断，不将推断自动当作已确认要求。

### 可直接复制的示例

```text
使用 $sky-req-prd-system，为以下已确定方案生成 PRD 和多状态线框原型。

项目：舆情监测系统，B 端 PC Web。
输出目录：/你的工作区/public-opinion-system，首版 v1.0。
本次在当前监测方案增加通知设置：
1. 风险等级 E1～E5 可多选，默认 E4、E5，允许空选。
2. 渠道为钉钉、飞书、微信、Email，可多选，默认空，允许空选。
3. 接收人或机器人已在其他位置配置，本页只选择渠道。
4. “推送重复数据”默认关闭，沿用现有判重结果。
5. 点击确认保存，只影响保存后的后续推送；等级或渠道为空时不推送。
请明确本次范围、字段与操作规则、保存及异常状态，并列出尚未确定的实施问题。
```

以上是合成方案，不代表真实业务约定。输出目录应替换为实际路径；后续维护保留该项目目录，不重新创建同名项目。

## 产出哪些物料

### 标准 PRD

默认按九章组织；内容按实际适用性填写，无依据的信息明确待确认，不为填章节编造要求。

| 章节 | 主要内容 |
| --- | --- |
| 1. 版本说明和范围 | 背景与目标、本版功能清单、做与不做、依赖、重要决策、基本信息 |
| 2. 用户与业务流程 | 角色、场景、关键任务、模块流程及必要业务对象 |
| 3. 功能需求与规则 | 模块与功能、前提、字段、操作结果、分类规则、异常、边界和验收 |
| 4. 数据与埋点 | 字段与指标口径、适用的事件、触发条件、数据验证 |
| 5. 非功能需求 | 本次涉及的性能、安全、兼容、可用性等要求 |
| 6. 验收与上线条件 | 验收范围、发布前提、监控、回退及效果验证安排 |
| 7. 里程碑与计划 | 阶段、依赖、责任与完成条件；未知事项不猜测 |
| 8. 风险与待决策 | 具体缺口、影响、处理状态和需决策事项 |
| 9. 附录与参考资料 | 术语、依据、附件及设计或接口资料引用 |

功能规则按“模块 → 功能 → 规则分类 → 具体规则”展开，保留关键条件、行为、结果和限制。本版功能清单中的功能名称可直接进入同版本详情。公共规则集中维护，其他位置引用；复杂分支用分项或表格，避免长段落混写。Web 中可导出完整 PRD Markdown。

### 原型与配套材料

- **多状态线框原型**：页面必要元素、原生控件、状态画面、编号标注及当前规则说明。
- **流程与状态图**：有真实流程才画流程图，覆盖适用的正常与异常分支；有状态流转才画状态图。必要时补模块子流程，不强造图。
- **测试与上线材料**：有独立执行步骤、分工或数据时生成，规则和验收复用 PRD 来源。
- **交付与审查信息**：变更影响、待确认问题、检查结果和可定位的原文入口。实际执行后的测试或上线结果另行登记，不预填成功。

## 怎样查看原型

- 顶部 Tab 切换**页面级状态**，例如初始、未填写校验、提交失败、加载失败、取消确认；下拉展开等小交互直接在画面中操作。
- 点击控件进行必要的局部操作；点击旁边独立编号查看标注，两个点击区域分开。
- 默认选中有效标注，左右选中编号均为蓝底白字；右侧先说明当前状态与后续处理，再展示该标注的直接规则。
- 必要的结果、异常和恢复通过“关联规则”按业务名称链接到同版本 PRD，不重复展开整套规则。状态说明使用业务语言，不根据元素技术编号变化推断新增或消失。
- 有业务含义的字段、只读数据、小操作均应标注；选择控件说明选项、数量、默认值、多选/单选、空选与结果等适用信息。
- 重复列表的同列或同类操作通常只标注一次，状态、权限或行为差异仍单独说明；减少重复编号不减少页面元素。
- 同一详情涉及多个页面或弹框时，上下使用**独立画板容器**，各自有标题。弹框画板说明触发与关闭方式，避免误认为页面常驻内容。

设计人员可据此核对各状态的元素和行为，再重新进行视觉设计。静态状态画面不等于完整业务交互系统。

## 修改已有物料

直接告诉 Agent 项目位置、版本、目标与期望变化；有页面深链接或规则编号时一并提供。

也可点击 Web 顶部“定位并交给 Agent”：原型中先点击目标编号，再打开按钮，复制当前页面、状态、控件和关联规则的上下文；PRD 中定位当前阅读需求。补充“哪个控件、原值改为什么、适用哪些状态”即可。未能确定目标时弹框会提示手动选择，不默认选中无关内容。例如：“推送频率单选框首次默认由实时改为每日，已有设置仍回显原值。”

```text
继续维护 /你的工作区/public-opinion-system 的 v1.0。
将通知设置中“推送重复数据”的默认值改为开启。
同步受影响的 PRD、原型初始状态、标注及验收，保留其他规则和页面。
```

```text
修改同项目 v1.0 的通知设置原型：把渠道改成两列排列，保留原生复选框。
只调整该页面布局，不改变业务规则，不生成新版本。
```

已有物料进入维护入口，按稳定编号或文档片段读取和修改。整页改版允许重做该页，并保留仍适用的规则、元素与关联；不会因此重写所有页面。保存有版本指纹、冲突检查和恢复记录，冻结内容不可直接覆盖。

修改后仍需构建、校验及相关路径复核。工具可能扫描或编译整个项目，但这不等于模型重新生成整套内容，也不承诺固定的 token 节省比例。

## 基于旧版本生成新版本

### 同一项目、同一 Web 入口

```text
项目总览与版本计划
▾ v1.0 · 基础通知设置
   需求文档
   页面原型
   其他适用物料
▾ v2.0 · 通知策略升级
   需求文档
   页面原型
   其他适用物料
```

版本在左侧按版本号自然升序排列，旧版在上、新版在下。每版保存独立完整物料，入口始终为同一项目的 `site/index.html`；深链接中的版本号区分历史与新版内容。

### 推荐这样提出需求

```text
使用 $sky-req-prd-system。
在已有项目 /你的工作区/public-opinion-system 中，基于 v1.0 新建 v2.0。
不要新建项目，不覆盖 v1.0，沿用原 Web 入口。

v2.0 的确定变更：
1. 增加“仅工作日推送”，默认关闭；工作日采用系统已有日历口径。
2. 保留 v1.0 的风险等级、渠道和重复数据规则。
3. 本次不增加日历配置、接收人配置或历史补推。
请继承仍适用的材料，更新本版功能清单、规则、受影响原型状态与验收。
```

Agent 会确认基线、检查现有改动，复制基线的完整物料到新版本，只修改本版变化及关联，最后构建同一个 Web。继承功能在本版清单中区分沿用、修改、新增或移除，不把所有继承内容都算作新增范围。

**应保留完整源项目。** 只有一张截图、单个 HTML 或别人部署的展示链接，不能保证恢复出可持续维护的版本来源。路径不明确时先定位已有项目。

### 当前版修订、新产品版本与交接快照

| 意图 | 使用方式 |
| --- | --- |
| 修复 v1.0 的规则、标注或页面 | 明确“修改 v1.0，不新建版本” |
| 在 v1.0 基础上规划下一版 | 明确项目目录、基线 v1.0、目标 v2.0 和变更范围 |
| 给开发保留一次不可覆盖的交付依据，工作稿继续修改 | 明确要求创建当前版本的交接快照；它归在该版下，不算新的产品版本 |

冻结、开发中或已发布版本内容只读；需修改时建立新的规划版本。规划稿也可作为明确指定的继承基线，但未确认事项不会因此变成已确认。新版本追加后刷新浏览器，才能加载更新后的菜单。

## 项目锁定、升级与交付准备

新建项目包含 `.skill-lock.json` 和 `.skill-runtime/<内容指纹>/`，保存实际使用的技能说明、脚本、模板及资源；版本号和文件摘要共同识别版本。本机技能更新后，普通维护命令自动转用项目内经校验的副本。根目录 `build.py` 也检查对应工具一致性。不要手改锁或副本，损坏时恢复完整源备份。

例如：本机已安装 `preview.34`，以前用 `preview.33` 生成的项目仍沿用 `preview.33`，刷新网页或普通修订不会自动采用新版。这个旧项目继续新建产品 `v2.0` 时，也沿用它的技能锁；产品版本迭代与技能升级是两个独立操作。

需要旧项目采用本次阅读器优化时，可以直接说：

```text
请将 /你的工作区/public-opinion-system 升级到技能 2.0.0-preview.34。
保留已有业务规则和页面内容，不重新生成整套方案。
先检查差异和本地修改，在副本验证后更新项目外壳及规划版资源，
保留冻结版本内容，并核对升级后的 PRD 和原型阅读路径。
```

升级后构建并刷新页面；冻结版本的原型内容资源不会自动替换，因此历史画面可能保留旧展示。新建独立项目则直接使用当前已安装的技能版本，并自动保存自己的锁。

```bash
# 只读查看锁定版本、候选版本、完整性及逐文件差异
python3 <skill>/scripts/project.py pin-status /项目
# 预览升级，包括规划版本资源、只报告而不覆盖的历史资源
python3 <skill>/scripts/project.py upgrade-shell /项目
# 明确采用候选版后执行：先在临时副本构建/检查，通过才改原项目
python3 <skill>/scripts/project.py upgrade-shell /项目 --apply
```

没有锁的现有 V2 项目可以检查，但工具写入前须明确采用版本并执行上述升级。不会倒推或伪造旧生成版本。升级备份保存在 `.upgrade-backup/`；历史技能副本保留，冻结版本内容保持。副本的自动校验不能替代浏览器验证；升级后 Agent 仍需核对典型路径。

交付时，Agent 先完成结构检查、对照输入的语义审查和浏览器验证，按现有审查入口登记带位置的证据，再运行：

```bash
python3 <skill>/scripts/prepare_delivery.py /项目 --url http://localhost:8801 \
  --input /原始方案.md --evidence /复核证据.json --out /项目外/本次交付
# 需要提前查看评审稿时显式追加 --draft
```

命令核对本机服务200及入口HTML身份，输出交付报告和两个地址：localhost打开地址、本地Web入口绝对路径；另给完整项目目录。`agent_todo` 是 Agent 应补查/修复的内容，`business_decisions` 是需要产品经理确认的真实口径，不要求产品经理逐项运行脚本。

全部复核记录齐全且无自动问题/待决策时，生成 `static-ready.zip`（下游查看，无Python文件）和 `source-ready.zip`（完整源项目及锁定技能、外部原始输入与复核证据）。未就绪默认只出报告，不伪称可开工；`--draft` 可输出名称和清单均标为评审稿的两份包。每包附文件摘要清单；目标目录须为空且位于项目外。源包排除Git、缓存、编辑临时备份和升级备份；当前源文件、历史版本及运行副本均保留，不能只备份静态包。自动检查与复核记录不能保证业务分支永不遗漏，也不等于真实产品验收。

## 查看与打包交付

每次生成或修改后的回复应给出：

```text
在线查看：http://localhost:端口/site/index.html#/v/v1.0/_prd/scope
本地 PRD Web 入口：/绝对路径/项目/site/index.html
打包目录：/绝对路径/项目/
```

localhost 地址只在运行服务的本机有效。接收方需要文件包或另行部署的地址；技能不会自动发布或向团队发送材料。

### 发给下游的静态交付包

查看生成好的 Web **不需要 `.py` 文件或 Python 环境**。打包应包含完整的 `site/`、版本画面及资源所在的 `versions/`，以及存在时的 `attachments/`、`outcomes/`。保持相对目录，解压后打开 `site/index.html`。图形库随包提供，常规阅读支持离线及文件直开；受浏览器策略限制时可改用静态 HTTP 服务。

不能只发送入口 HTML 或 `site/`：原型和附件可能引用目录外的相对资源。可从完整项目副本中排除构建用 `.py`、缓存与临时编辑备份，打包前检查 PRD、各原型状态、图与附件均可读取。可用下述 prepare_delivery.py 自动打包；完整源项目另存一份。

### 自己保留的维护项目

保留完整项目，包括 `project.json`、各版本内容源文件、构建用 `.py`、资源与附件。后续 Agent 修订、构建和新增版本需要这些文件；静态交付包不应作为唯一备份。发包前检查历史版本、附件及其他资料是否都允许分享。

## 审查与质量边界

可单独要求审查，先看问题再决定是否修改：

```text
请审查 /你的工作区/public-opinion-system 的 v2.0，暂不修改。
检查原始方案是否覆盖、范围和规则是否明确、必要状态是否缺失、
PRD 与原型标注是否一致，以及是否存在重复或无关内容。
列出具体位置、证据、影响与修复建议，并区分已检查和未复核项。
```

检查包括数据与引用、构建时效、规则和验收关联、原型控件属性、状态覆盖及变更影响；语义判断和实际浏览器检查另行记录。自动检查通过不代表业务方案已被确认，也不等于真实产品测试通过。

影响范围、权限、核心结果或验收的未决问题会明确标为实施阻塞。其他未知项列为待确认，不通过虚构参数让报告“通过”。生成成功可能只是可评审草稿，应结合质量报告和业务确认判断能否交付实施。

保留完整维护源项目与交付包；Agent 对照原始方案完成内容与浏览器复核，业务待决策仍由产品经理确认。固定版本与升级方式见[项目锁定、升级与交付准备](#项目锁定升级与交付准备)。

## 命令行与仓库说明

日常使用可直接对话，以下命令供维护者定位和排查。`<skill>`、`<项目>` 等为实际绝对路径占位，不要原样执行。

```bash
# 查找已有项目
python3 <skill>/scripts/project.py discover <工作区>

# 基于旧版追加新版；只创建继承结构，方案变更仍需 Agent 编写
python3 <skill>/scripts/project.py new-version <项目> \
  --version v2.0 --from-version v1.0 --name "通知策略升级"

# 编译与校验
python3 <项目>/build.py
python3 <skill>/scripts/validate.py <项目> --report <项目>/quality-report

# 读取一条规则，不输出整份 PRD
python3 <skill>/scripts/revise_item.py <项目> --version v2.0 --id RULE-DUP --read

# 在项目根启动只读静态服务；端口按实际情况选择
python3 -m http.server 8795 --bind 127.0.0.1 --directory <项目>

# 取得交付地址；需另确认服务实际可访问
python3 <skill>/scripts/delivery_info.py <项目> --url http://localhost:8795
```

### 快速预览合成示例

```bash
python3 scripts/create_static_demo.py /空的预览目录
python3 -m http.server 8766 --bind 127.0.0.1 --directory /预览目录
```

打开 `http://localhost:8766/site/index.html#/v/v0.1/prototype/create-order`。合成示例故意保留字段与权限等实施缺口，默认质量结果为 incomplete；它用于展示评审材料，不代表已认可的业务或接口契约。
