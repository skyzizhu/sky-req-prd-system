# 需求深化与交付口径

生成需求、测试、上线材料或修订规则时读取。正式浏览器 PRD 及原型属性编辑见 editing.md；交接修订号仍按 PLAN.md 的实际进度说明。

## 先深化，再生成

读取用户输入、已有需求和公司配置；为本次功能列出已知事实、建议方案、未决问题及排除项。优先询问改变业务结果、权限或范围的问题；有充分授权和资料时直接推进。没有依据的阈值、指标和角色权限标 pending，不通过扩写把假设变成事实。

**适当挖掘**：产品经理的输入常是零散的产品需求（已转换，非用户原话）；过于简洁或泛化时，应主动按功能类型补充细颗粒度（边界、异常、状态转换、验收实例），全部标注「AI 推断 + 待确认」走评审转正——小颗粒度不可能都由输入给出，挖掘是职责而非越权；但业务决策（阈值、方案取舍、优先级）仍须问或标待确认，不得代拍板。

**细目完整性覆盖维度**（每个功能需求的 rule_details 逐维度核对，缺则补，宁多勿漏）：
① 功能行为（正常路径）；② 输入与校验（格式、范围、非法输入）；③ 边界与极端（上限/下限/最小/超大输入）；④ 异常与失败（失败提示、失败重试、依赖不可用）；⑤ 状态与恢复（切后台/中断/刷新后恢复）；⑥ 权限与降级（权限被拒的降级路径）；⑦ 处理中锁定（进行中防不一致、防重复）；⑧ 一致性与防漂移（按时间戳/按来源计算，不累积误差）；⑨ 可访问性（语义标签、对比度、键盘可达）；⑩ 依赖拉取（远端资源按需获取与失败提示）。每条细目带分类、实例，可独立开发与验收。

按实际功能选择检查维度，不要求无关矩阵：
- 表单：字段含义、必填条件、默认值、格式、长度/精度、校验时机、错误定位与保留输入。
- 列表：数据权限、排序、筛选组合、分页、空结果、返回和刷新后的状态。
- 生命周期：起止状态、角色、触发事件、前置条件、失败、重复操作和冲突处理；复杂时用状态表。
- 批量：选择范围、上限、部分成功、失败明细、重试和幂等业务预期。
- 指标：对象、公式、时间与时区、去重、单位、刷新、空值。

用具体实例核对规则。例：取消订单不能只写“支持取消”；应明确状态、角色、成功结果、失败处理，以及是否涉及库存/退款等依赖。无关依赖不强加。

## 优先级与自动功能清单

需求可带可选 `priority`（P0～P3，省略标待定）；功能章节顶部由 spec 自动生成功能清单表（编号/功能/优先级/来源/状态），不手工维护第二份清单文档。P0 需求必须有验收口径（audit 检查缺口）。

## 数据与埋点章节结构（借鉴经验证项目沉淀）

埋点章按「原则 → 核心指标口径表 → 事件表 → 看板组织 → 溯源」组织。原则至少含：口径唯一（与上线观察同源）、最小必要、匿名会话、零侵入上报——纯前端组件保持自身零网络请求，事件经回调由宿主统计通道上报，独立运行不上报。指标口径表每行写定义与分母口径（排除项显式列出）；事件表每行写事件名（snake_case）、触发时机、关键参数；看板组织按使用场景分组。无埋点决策也必须显式标注不适用并给原因，不得留空。

## 可选结构化深化数据

保留既有 requirements.rules 兼容；新建或深改需求采用 requirement.rule_details 数组，稳定 ID 不随标题变更。该数组存在时是细粒度规则唯一来源，边界与异常融合为对应 category 的细目；rules 可整体省略或仅保留不重复的背景说明，避免与细目重复。每条格式：

```json
{"id":"RULE-NAME-LENGTH","category":"validation","statement":"去除首尾空格后长度为 1～40 个字符","source":"ai-inferred","status":"pending","examples":[{"input":"空字符串","expected":"拒绝提交并定位名称字段"}],"acceptance_ids":["AC-ORDER-001"]}
```

category 按业务填写（如 permission、validation、state、data、feedback），不限制固定目录数量。与当前需求的 acceptance ID 关联。AI 补充条目保持 pending，直到有确认依据。声明和实例必须人工/Agent 核对业务一致性，自动检查不能证明语义正确。

## 标准输出及公司约定

沿用 nodes.md 六类材料，按本次范围裁剪。读取 config.md 的公司术语、角色、数据口径、组件库和文档格式，记录约定来源及适用版本。产品表达业务语义；API、数据库和技术实现建议明确标为待开发确认，不冒充既有契约。

原型覆盖业务只读数据与可操作控件。字段说明包含语义、类型、单位、枚举、空值与例子；场景覆盖角色与业务状态，不用无效按钮模拟范围外能力。

## 测试与上线

实际执行、指标观测及下一版跟进使用 outcomes.md 的正式台账和结果视图；用例生成本身不产生通过结果。冻结后追加观察不改写版本内容。

**测试用例标准格式**（借鉴经验证项目沉淀）：按功能模块分组（一组对应一个功能需求），表列为「编号 / 前置 / 步骤 / 预期 / 关联」；顶部写执行环境（浏览器矩阵、file:// 与宿主两种方式）与「用例已生成 ≠ 已执行」的登记提醒；文末给覆盖对照（AC 与视觉类细目的承载方式）与回归范围。步骤编号化、预期落到可观察表现并量化（阈值、格式、会话语义），异常降级（依赖不可用、权限被拒、存储受限）单独成条。

**上线条件四类结构**：A 需求与决策（产品侧拍板，拍板结果回写 spec 转已确认）→ B 系统功能条件（开发侧逐条可验证：功能完整、精度阈值、降级路径、隐私的技术前提，注明验证手段）→ C 兼容与环境（浏览器/运行方式/视觉矩阵，不达标项记入已知问题清单）→ D 质量与流程（测试通过且登记台账、发布窗口确认、回退方式）。A/B/D 全部满足才可发布。

**AB 实验页结构**：前置依赖（埋点已接入，无埋点无法度量）→ 实验假设 → 分组与流量 → 核心指标 + 护栏指标 → 样本量与时长 → 胜出标准与回退 → 实验纪律（先评审后放量、不提前下结论、结果记入台账、单地域结论不外推）。多实验串行，避免交叉。

每个重要规则关联验收和具体实例；测试描述包含前置条件、输入、步骤、可观察结果、优先级及规则 ID。按风险补充边界、权限、状态转换、失败/重试、并发业务预期及回归范围；不要穷举无意义组合。

**验收条目标准**：每条验收（AC）与需求规则一一对应、自身详尽可独立执行——前置、操作、可观察预期俱全；AC 全集必须有用例承载，执行结果登记台账（有记录不代表通过）。

**验收覆盖状态机**：AC 集合须覆盖状态机全部维度（参照 prototype.md 状态机全覆盖标准十二类），尤其是异常与边界状态（校验失败、权限降级、资源不足、网络异常、后台恢复、并发锁定）——这些最容易被遗漏但也是开发最容易出 bug 的地方。

分别记录：用例已生成、原型已执行、真实产品已执行。执行结果包含环境、时间、执行人/工具、结果与证据。没有实际执行就不能写通过。

上线目标按“问题 → 预期变化 → 指标定义/公式 → 基线 → 目标 → 数据来源 → 观察周期 → 负责人 → 未达标行动”填写。基线、阈值未知则待确认。按需要补充质量护栏、放量/暂停/回滚条件；上线后记录实际结果与下一步决策。

## 检查与修改

运行 `python3 <skill>/scripts/audit_quality.py <项目> --version <版本>` 输出规则完整性缺口；`--strict` 在存在缺口时退出 1，适合明确要求完整深化的检查。旧版本未声明 rule_details 时报告缺口而不改写历史，不将此报告作为既有 build/freeze 的新增硬门槛。

质量报告只检查已记录数据：没有缺口不等于业务正确或开发已经认可。结合已有 validate 和关键交互操作，再给出剩余决策项。

正式 PRD 编辑使用 editing.md 的本机编辑器或命令；原型行为修改仍由 Agent 完成：先 impact，修改关联规则、脚本和测试，检查旧值残留，验证后 checkpoint。浏览器批注仍是评审意见。自动联动不完整时逐项列出待复核内容。
