# 节点清单与菜单骨架

产品方案站点的一级菜单（模块）与二级菜单（页面）由「固定节点 + 条件节点」组成。

**布局约定**：需求文档模块使用 `layout: "continuous"`——所有二级页拼接为一个连续长页，二级菜单作为锚点导航（点击平滑滚动到对应章节，滚动时菜单高亮反向联动）；其他模块默认分页（`pages`）。

## 固定节点（任何产品必须生成）

| 模块 | 页面 | 内容要求 |
|---|---|---|
| 待确认清单 | （自动聚合页） | 站点自动生成，无需写内容文件；skill 需保证 pending 项准确 |
| 产品概览 | 产品定位 | 定位（一句话/平台/形态）、**产品目标（商业目标 + 用户目标 + 北极星指标）**、目标用户、竞品与差异化、核心价值、版本记录 |
| 需求文档 | 功能清单 | 全量功能索引表（模块×功能×说明×优先级×FR编号×状态）+ 统计行 |
| 需求文档 | 功能需求详述 | 按模块分页；FR 编号表格 + 分类规则 + **异常与边界小节（强制：失败路径/权限网络异常/极值）** + 溯源引用块 |
| 需求文档 | 用户故事与场景 | US 编号表（角色/故事/优先级）+ 关键场景（前置/步骤/预期）+ 优先级约定（P0/P1/P2） |
| 需求文档 | 整体流程图 | Mermaid flowchart，端到端主流程 |
| 需求文档 | 非功能需求 | 性能、安全与隐私、兼容性、可靠性（按产品形态裁剪，至少性能+安全） |
| 需求文档 | 风险与依赖 | 风险表（编号/风险/等级/影响/应对）+ 依赖 + 开放问题 |
| 需求文档 | 名词解释 | 术语表 + 全站文档约定（FR/US/AC/TC/R 编号规则、徽标语义） |
| 原型图 | 页面总览 | **标注阅读说明（四色分级表 + 读图方法 + 序号约定）** + 页面清单表 + 跳转关系 mermaid 图 |
| 原型图 | 各页面 | 每个关键页面一个线框页（序号徽章标注），菜单项自动带 `01 ·` 序号，规范见 prototype.md |
| 测试 | 验收标准 | Given/When/Then 表 + 状态 |
| 测试 | 测试用例 | TC 编号用例表（前置/步骤/预期） |
| 上线目标 | 目标与里程碑 | 上线目标（口径+达标线）、里程碑表 |
| 上线目标 | 上线 Checklist | `- [ ]`/`- [x]` 勾选清单，按上线前/中/后分组 |

## 条件节点（内容涉及才生成；归纳清单中说明判断依据）

| 页面 | 判定依据 | 形式 |
|---|---|---|
| 数据埋点 | 有数据衡量目标 / 需要指标看板 / 有北极星指标 | md：埋点原则 + 事件表（事件/时机/参数）+ 看板口径 |
| 整体信息图（信息架构） | 产品结构复杂、多层级导航 | html-embed：卡片树 |
| 泳道图 | 多角色 / 多系统协作 | mermaid：subgraph 分泳道 |
| 状态图 | 核心实体有复杂生命周期（>3 状态） | mermaid stateDiagram-v2 |
| 时序图 | 有接口调用链 / 前后端交互 | mermaid sequenceDiagram |
| 权限与角色 | 多角色系统（管理员/普通用户…） | md：角色×权限矩阵 |
| 接口需求 | 前后端分离 / 开放 API | md：接口清单表 |
| 数据模型 | 有实体存储设计 | md：实体/字段/关系表 |
| 竞品分析 | 市场导向型新产品（概览页差异化一节不满足时） | md：竞品对比矩阵 |
| 运营需求 | 需要运营配置位/活动位 | md：运营位说明 |
| 法务合规 | 金融/医疗/隐私敏感行业 | md：合规要求清单 |
| 交互规范 | 多页面复杂交互 / 全局快捷键体系 / 手势体系 | md：快捷键表 + 手势表 + 空态/加载态/错误态统一约定 + 反馈规范（toast/提示音/震动） |
| 国际化 i18n | 出海 / 多语言市场 | md：语言清单、文案管理方式、RTL、日期数字格式 |
| 灰度与 AB 实验 | 增长导向 / 有需实验验证的改动 | md：实验假设、分组与流量、核心指标、放量计划 |
| 发布渠道策略 | 多渠道分发 / 涉及应用商店审核 | md：渠道清单、各渠道审核要求、版本策略 |

判定原则：宁缺勿滥——没有对应内容就明确不生成，并在归纳清单里写「未纳入 X：输入中无相关信号」。生成过的条件节点在更新时若内容被移除，需提示用户是否下架该页面。

## 受众端型（C / B / G）→ 内容侧重

`product.audience`（c/b/g）决定生成时的内容侧重，与 form（载体）、ends（多端）正交：

| 维度 | C 端（消费者） | B 端（企业） | G 端（政务） |
|---|---|---|---|
| 产品目标 | 北极星指标、留存、DAU、口碑 | 续约率、采用率、效率量化（省时/省钱） | 合规通过、验收标准、覆盖率 |
| 条件节点倾向 | 数据埋点、竞品分析大概率纳入 | **权限与角色几乎必出**；泳道图（多角色审批）、接口需求、数据模型倾向纳入 | **法务合规几乎必出**（等保/信创/数据主权） |
| 非功能侧重 | 性能、体验、兼容 | 审计日志、数据导出、SSO/集成、稳定性 | 加密强度、国产化适配（芯片/OS/DB）、操作留痕 |
| 用户故事 | 场景化、情感化（US 写用户动机） | 角色化：用户≠购买者，区分决策链（管理员/普通员工） | 流程化、责任制（经办/审核/领导） |
| 原型取向 | 引导流、空态情感化、动效说明 | 表格密度高、筛选器/批量操作、角色视角切换 | 保守规范、较大字号、审批流页面、少花哨交互 |

判定依据示例：输入出现"企业内部/客户管理/ERP/工作流/审批（商业语境）"→ b；"政务/机关/单位/等保/信创"→ g；"大众用户/App 市场/社交/内容"→ c。推断不出与形态合并一次提问。

## 多端产品的菜单骨架

识别到 `product.ends`（如 C 端 App + web 管理后台）时：

```
待确认清单 → 产品概览 → 需求文档（功能清单含「端」列）→
原型图 · App 端（页面总览 + 各页面）→ 原型图 · 管理后台（页面总览 + 各页面）→
测试 → 上线目标
```

- 测试与上线目标通常跨端共用一份；若两端节奏不同，也可按端拆分（用户确认）。
- 需求文档不分端拆模块（同一功能可能跨端），用功能清单与 FR 表的「端」列表达归属；端归属不明的功能在归纳阶段列为待确认。

## 产品形态 → 需求内容影响

形态不只影响原型（见 prototype.md），也影响需求文档侧重：

- **web / h5**：兼容性（浏览器矩阵）、响应式断点、SEO（如对外）
- **desktop**：系统版本/架构兼容、常驻资源占用、系统权限
- **mobile**：机型适配、弱网、离线、推送、应用商店审核
- **miniapp**：平台规范、包体积限制、审核类目
- **tv**：遥控器导航、焦点态、10 英尺观看距离、大字号
